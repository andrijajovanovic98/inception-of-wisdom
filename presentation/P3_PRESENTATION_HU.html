Part 3: Wisdom Loop — Autonóm Hibajavítás és Visszaállítás

A Wisdom Loop a diagnózisból kiindulva ellenőrzött forráskód-javítást végez. Összehangolja a diff-mentes JSON javítócsomagokat, a többlépcsős érvényességi ellenőrzést (sanity bounds), az atomikus Git ágkezelést, a Docker konténer újraindítást, a türelmi időszakos aktív verifikációt és a legfeljebb 3 próbálkozás utáni automatikus visszaállítást (rollback).

Subject (V.3, fordítás): "Egy diagnózisból a hurok patchet készít, alkalmazza, commitol, újraindítja a célt, és eldönti, hogy eltűnt-e a tünet." — "Három sikertelen kísérlet után a Wisdom Loop visszatekeri az auto-heal ágat a pre-loop revízióra (az ágens commitjai elérhetetlenné válnak), az eredeti kódon indítja újra a célt, és tiszta hibát jelez a dashboardon."

Diff-mentes JSON Patch generálás (p3/patcher.py)

Miért buknak el az Unified Diff-ek kis modelleknél?

A hagyományos diff formátum (@@ -12,4 +12,6 @@) szigorú sorszámozást és karakterszámlálást igényel. A 3B paraméter alatti helyi modellek hajlamosak hibás fejléceket generálni, amit a standard patch(1) parancs elutasít.

Strukturált Teljes Fájlcsere

{
  "summary": "Az indulási kódnak szükséges Flask import visszaállítása",
  "files": [
    {
      "path": "demo_app/app.py",
      "op": "modify",
      "content": "... a teljes módosított fájl ..."
    }
  ]
}
  • A content a teljes módosított fájl; az op create, modify vagy delete. Diffet nem fogad el.
  • Nincs előre megírt javítás: nagyobb fájlnál a modell csak a traceback által mutatott chunkot írja újra (sima kódként), a patcher pedig ezt illeszti be a JSON patch teljes fájltartalmába. Az analyst.patch_strategy: full_file esetén a modell maga írja a teljes JSON patchet (egy 1.5B modell megcsonkítja a fájlt — mérve 0 a 9-ből).
  • A változatlanul visszaadott, vagy a hibát csak áthelyező válasz (új raise / exit(), feltételhez kötött szerverindítás) még a kísérleten belül újrakérésre kerül — mielőtt egy újratelepítésbe kerülne.

Érvényességi Korlátok és Védelmi Falak (p3/sanity.py)

Lemezre Írás Előtti Szigorú Szűrés

Mielőtt egy patch megérintené a fájlrendszert vagy a Git tárolót, át kell mennie a subject négy szabályán, és további négyen:

  • Fájlszám korlát: legfeljebb 3 fájl patchenként.
  • Triviális placeholder: nem üres fájlból nem lehet csonk (pass, ..., egy docstring); nem kerülhet be új # TODO vagy rest of code unchanged.
  • Zsugorodás elleni védelem: legfeljebb 60%-kal lehet kisebb az eredetinél, bármit mond az op (egy létező fájl fölé írt create is számít, egy nem üres fájl törlése 100%-os zsugorodás), és bármekkora a fájl.
  • RAG markerek: a prompt vázai (--- File: ... ---, --- Code Snippet #n ---, régióhatárok) nem szivároghatnak a kódba.
  • Hatókör: csak a demo_app/-on belül, soha az operátor iow.config.yml-je.
  • Parse-olható és változtat: az ast.parse-nak sikerülnie kell, és a fájllal azonos patch elutasításra kerül.
  • Nem tűnhet el definíció: az újraírás nem hagyhat el olyan importot vagy konstanst, amelyet a fájl még használ.
  • Nincs beállítás előtti olvasás: ha a port csak egy if-ben, vagy egy olyan try-ban kap értéket, amelynek except-je továbbfut, a patch elutasításra kerül (NameError lenne az újratelepítés után).

Git Izoláció és Atomikus Commitok (p3/git_manager.py)

Dedikált Öngyógyító Ág

  • Minden autonóm módosítás az izolált iow/auto-heal ágon fut.
  • Pre-loop revízióként rögzíti a demo_app/ pontos futó állapotát: a HEAD-et, ha a fa egyezik vele, különben egy snapshot commitot (a nem commitolt, ültetett hibával együtt), és a ciklus végéig a refs/iow/pre-loop-ban tartja.
  • Atomikus fájlírás: *.iow.tmp + fsync + os.replace, a fájlmód megmarad.
  • Git plumbinggal commitol, a tárgysort a diagnózisból generálja: a HEAD, az index és a kicheckoutolt ág nem mozdul.

Bájtra Pontos Rollback

Bizonyítva, nem feltételezve: 3 sikertelen kísérlet után az iow/auto-heal visszaáll a pre-loop revízióra, a demo_app/ pedig egy eldobható indexen át (read-tree + checkout-index) helyreáll belőle. A fát újrahash-eli és összeveti: a dashboard identical-t mutat. Az operátor iow.config.yml-je megmarad, a ciklus közbeni szerkesztés pedig előbb a refs/iow/overwritten/<idő> alá mentődik.

Konténer Újraindítás és Verifikáció (p3/verifier.py)

Docker Engine Újraindítás

  • A host Docker démonnal kommunikál a /var/run/docker.sock-on keresztül.
  • Alapértelmezetten a Docker Engine API-val indítja újra a célkonténert.
  • IOW_REDEPLOY_MODE=gitops esetén helyette push-olja a commitot, és megvárja a podot, amelyet az Argo CD indít belőle (a commit a kódja hash-ét a pod sablonba írja).
  • Lekéri az új állapotot és kilépési kódot.

Aktív Türelmi Időszak (Grace Period, 20s)

  • Megvárja, amíg a cél egyszer válaszol (boot_timeout), csak utána indul a türelmi idő.
  • Újra elküldi azt a kérést, amely összeomlasztotta a célt — a cél saját logjából olvasva (a Flask Exception on /api/crash [POST] sora, az 5xx access sor): egy olyan végponton lévő soft crash, amelyet egyik szonda sem hív, nem mehet át gyógyultként.
  • Bármely crash esemény, az új folyamat nem-nulla kilépése vagy hibázó szondák a türelmi idő alatt elbuktatják a kísérletet.

Többfordulós Visszacsatolási Hurok (p3/loop.py)

Adaptív Öngyógyítás

Egyetlen javítás nem mindig elég komplex hibáknál. A Wisdom Loop 3 fordulón keresztül tanul a hibákból:

1. Kísérlet: Diagnózis -> Patch -> Újraindítás -> Verifikáció Elbukik!
                 │
                 ▼ (Visszacsatolás: Konténer kilépési kód: 1, Traceback log átadva)
2. Kísérlet: Bővített prompt az előző hibával -> Új patch -> Sikeres!
                 │
                 └─ Ha a 3. kísérlet is bukik: rollback a pre-loop revízióra (identical)
  • Az új hibanapló — az újraindítás óta a démontól olvasva — visszamegy az Analysthez.
  • A következő patch prompt megtudja, mi bukott el (és hogy a saját módosítása okozta-e), szabadabban mintavételez (hőmérséklet 0.1 / 0.4 / 0.7), környezeti hibáknál pedig megkapja a cél portját és környezetét, a konténeréből olvasva.

Üzemeltetési Korlátok (p3/safety.py)

iow.config.yml Korlátok

  • Single-Flight Lock: Egyszerre kizárólag egyetlen javítási hurok futhat.
  • Cooldown: Azonos incidensszignatúránál 300 mp kötelező csendes periódus.
  • Rate Limit Per Hour: Legfeljebb 5 javítás egy gördülő 60 perces ablakban.
  • Hard Cap: Folyamatonként legfeljebb 20 javítás.

Vészhelyzeti Kill-Switch

Subject követelmény: A kill_switch: true beállítás az iow.config.yml fájlban azonnal leállít minden autonóm műveletet az ágens újraindítása nélkül!

Part 3 Védési Ellenőrzőlista

Tipikus Értékelői Kérdések és Válaszok:

  • K: Miért nem hagyományos git diff formátumot használtok?
    V: A 3B alatti modellek sorszám-eltolási anomáliákat okoznak. A strukturált teljes fájlcsere megbízható és szintaktikailag biztonságos.
  • K: Mi gátolja meg, hogy a modell letörölje a teljes projektet a 'javítás' kedvéért?
    V: A sanity kapu, minden lemezre írás előtt: max 3 fájl, nem lehet triviális placeholder, max 60% méretcsökkenés, nem tűnhet el definíció, nem olvashat beállítás előtti értéket, és a kódnak parse-olhatónak kell maradnia.
  • K: Hogyan demonstráljátok a rollback működését a védésen?
    V: Leállítjuk a modellt (hoston make stop, Dockerben docker stop iow_ollama), hibát ültetünk, és végignézzük a 3 sikertelen kísérletet, majd a rollbacket: a demo_app/ visszahash-elődik a pre-loop fára (identical), a független munka érintetlen.
