Part 3: Wisdom Loop - Autonóm Hibajavítás és Visszaállítás

A Wisdom Loop a diagnózisból kiindulva ellenőrzött forráskód-javítást végez. Összehangolja a diff-mentes JSON javítócsomagokat, a többlépcsős érvényességi ellenőrzést (sanity bounds), az atomikus Git ágkezelést, a Docker konténer újraindítást, a türelmi időszakos aktív verifikációt és a legfeljebb 3 próbálkozás utáni automatikus visszaállítást (rollback).

Subject követelmény: "Cselekedj a diagnózis alapján: készíts patch-et, alkalmazd a módosításokat, igazold a konténer helyreállását. Tartsd be a biztonsági korlátokat (rate limit, cooldown, hard cap, kill-switch). Sikertelen verifikáció esetén automatikus visszaállítás maximum 3 kísérlet után."

Diff-mentes JSON Patch generálás (p3/patcher.py)

Miért buknak el az Unified Diff-ek kis modelleknél?

A hagyományos diff formátum (@@ -12,4 +12,6 @@) szigorú sorszámozást és karakterszámlálást igényel. A 3B paraméter alatti helyi modellek hajlamosak hibás fejléceket generálni, amit a standard patch(1) parancs elutasít.

Strukturált Teljes Fájlcsere

{
  "summary": "ZeroDivisionError kezelése guard feltétellel",
  "files": [
    {
      "path": "demo_app/app.py",
      "op": "replace",
      "content": "... teljes szintaktikailag helyes forráskód ..."
    }
  ]
}
  • A modell teljes fájlt ír felül vagy hoz létre.
  • Nincsenek pontatlan eltolási (offset) anomáliák.
  • A system prompt szintaktikailag zárt, teljes kódot követel meg.
  • Ha a generált patch elbukik, a sebészi fallback célzottan hatástalaníthatja az ismert szándékos crash markert.

Érvényességi Korlátok és Védelmi Falak (p3/sanity.py)

Lemezre Írás Előtti Szigorú Szűrés

Mielőtt egy generált patch megérintené a fájlrendszert vagy a Git tárolót, át kell mennie 4 védelmi kapun:

  • Fájlszám korlát: Legfeljebb 3 fájlt módosíthat egyetlen javítási körben (megelőzi a teljes repó szétzilálását).
  • Zsugorodás elleni védelem (Shrinkage Guard): Legfeljebb 60%-kal csökkenhet a fájl mérete az eredetihez képest (kivédi a kód véletlen kiürítését).
  • Helyettesítő token védelem: Letiltja a lusta AI mintákat: # TODO, # rest of code here, # implement here.
  • Szintaktikai ellenőrzés: Python fájloknál lefuttatja az ast.parse(content) hívást; szintaxishiba esetén a patch azonnal elutasításra kerül.

Git Izoláció és Atomikus Commitok (p3/git_manager.py)

Dedikált Öngyógyító Ág

  • Minden autonóm módosítás az izolált iow/auto-heal ágon fut.
  • A ciklus előtt rögzíti a kiinduló állapotot: pre-loop revision (commit SHA).
  • Atomikus fájlkezelés: ideiglenes fájlba ír, majd biztonságos átnevezést végez.
  • Git commitot hoz létre a diagnózis összefoglalójával és a kísérlet sorszámával.

Hatókörös Mixed Rollback

Védett Munkakönyvtár: Ha mindhárom verifikáció sikertelen, a GitManager mixed resetet és kizárólag a demo_app/ célzott visszaállítását végzi. A másutt lévő nem commitolt ágens- és dashboard-munka megmarad.

Konténer Újraindítás és Verifikáció (p3/verifier.py)

Docker Engine Újraindítás

  • A host Docker démonnal kommunikál a /var/run/docker.sock-on keresztül.
  • Alapértelmezetten a Docker Engine API-val indítja újra a célkonténert.
  • IOW_REDEPLOY_MODE=gitops esetén Argo CD/kubectl rolloutra vár.
  • Lekéri az új állapotot és kilépési kódot.

Aktív Türelmi Időszak (Grace Period, 20s)

  • Nem fogadja el azonnal a helyreállást pusztán a konténer elindulása miatt.
  • A / és /healthz végpontokat teszteli a türelmi idő alatt.
  • Az /api/crash kizárólag a make break szándékos hibatriggere, nem health probe.
  • Pásztázza a konténer logjait, hogy nem lép-e fel azonnali újabb crash loop.

Többfordulós Visszacsatolási Hurok (p3/loop.py)

Adaptív Öngyógyítás

Egyetlen javítás nem mindig elég komplex hibáknál. A Wisdom Loop 3 fordulón keresztül tanul a hibákból:

1. Kísérlet: Diagnózis -> Patch -> Újraindítás -> Verifikáció Elbukik!
                 │
                 ▼ (Visszacsatolás: Konténer kilépési kód: 1, Traceback log átadva)
2. Kísérlet: Bővített prompt az előző hibával -> Új patch -> Sikeres!
                 │
                 └─ Ha a 3. kísérlet is bukik: hatókörös demo_app/ mixed rollback
  • Az 1. kísérlet hibaüzenete és tracebackje beépül a 2. kísérlet promptjába.
  • Lehetővé teszi, hogy az 1.5B modell korrigálja a korábbi tévedéseit.

Üzemeltetési Korlátok (p3/safety.py)

iow.config.yml Korlátok

  • Single-Flight Lock: Egyszerre kizárólag egyetlen javítási hurok futhat.
  • Cooldown: Azonos incidensszignatúránál 300 mp kötelező csendes periódus.
  • Rate Limit Per Hour: Legfeljebb 5 javítás egy gördülő 60 perces ablakban.
  • Hard Cap: Folyamatonként legfeljebb 20 javítás.

Vészhelyzeti Kill-Switch

Subject követelmény: A kill_switch: true beállítás az iow.config.yml fájlban azonnal leállít minden autonóm műveletet az ágens újraindítása nélkül!

Part 3 Védési Ellenőrzőlista

Tipikus Értékelői Kérdések és Válaszok:

  • K: Miért nem hagyományos git diff formátumot használtok?
    V: A 3B alatti modellek sorszám-eltolási anomáliákat okoznak. A strukturált teljes fájlcsere megbízható és szintaktikailag biztonságos.
  • K: Mi gátolja meg, hogy a modell letörölje a teljes projektet a 'javítás' kedvéért?
    V: A Sanity ellenőrzések: max 3 fájl, max 60% méretcsökkenés, és kötelező AST szintaktikai érvényesítés a lemezre írás előtt.
  • K: Hogyan demonstráljátok a rollback működését a védésen?
    V: Szándékosan feloldhatatlan hibát idézünk elő; 3 sikertelen kísérlet után ellenőrizzük, hogy csak a demo_app/ tért vissza a kiinduló állapotba, a független munka pedig megmaradt.
