42 VIENNA — AUTONÓM ÖNGYÓGYÍTÓ ÁGENS

Inception of Wisdom (IoW)

Egy 100%-ban helyi, autonóm öngyógyító ágens-hurok, amely folyamatosan felügyel egy konténerizált szolgáltatást, észleli a hibákat, szemantikus RAG-kereséssel kontextust gyűjt, diff-mentes JSON javítást szintetizál, és sikertelenség esetén a Git segítségével automatikusan visszaállítja a kódot.

Szigorú Subject Szabály: Minden kizárólag helyben futhat. Távoli LLM szolgáltatás (OpenAI, Anthropic, Gemini) bármilyen hívása tilos, és nulla pontos értékelést von maga után.
Navigáció: Jobbra nyíl vagy Következő gomb.

A 4-Ütem: Autonóm Öngyógyító Hurok

A rendszer egy folyamatos, zárt 4-ütemű ciklust valósít meg állapot-visszacsatolással:

 ┌──────────────┐         Hiba Észlelése           ┌──────────────┐
 │ 1. OBSERVE   ├─────────────────────────────────►│ 2. THINK     │
 │  (Observer)  │    (Regex logok, 5xx szondák)    │  (Analyst)   │
 └──────▲───────┘                                  └──────┬───────┘
        │                                                 │ Releváns AST chunkok
        │ Verifikáció                                     │ & LLM Diagnózis
        │ (20s Grace Period)                              ▼
 ┌──────┴───────┐        Atomi Fájl Patch          ┌──────────────┐
 │ 4. VERIFY    │◄─────────────────────────────────┤ 3. ACT       │
 │  (Verifier)  │      Commit az iow/auto-heal-en  │ (Wisdom Loop)│
 └──────────────┘                                  └──────────────┘
  (3 sikertelen kísérlet után csak a demo_app/ hatókör áll vissza)

Jelosztályozási Döntési Fa

A rendszer nem végez vaktában javítást. A hard jelek (crashek, 5xx hibák, nem-nulla exit) azonnal indítják a hurkot, míg a soft szuggesztiók (4xx hiányzó végpontok) csak megjelennek a dashboardon az ember számára.

Önkorlátozó Biztonság

Szigorú korlátok: max 3 próbálkozás egy ciklusban, írás előtti sanity ellenőrzések, single-flight zár, cooldown és dinamikus vészleállító (kill switch).

Konténerizáció és Helyi LLM

Egyetlen docker compose up

  • make up = docker compose up --build -d: az ágens, az LLM futtatókörnyezet, a célalkalmazás és a Gitea.
  • demo_app: Flask célalkalmazás (5001:5000 port), ./demo_app:/app kötéssel, STOPSIGNAL SIGINT-tel — egy újraindítás jóval egy másodperc alatt van.
  • agent: dashboard a :8000 porton; csatolva a Docker socket ($DOCKER_SOCK, campuson a rootless socket), a repó a /workspace-be és a /tmp/iow.
  • Fájltulajdonos: a scripts/agent_entrypoint.sh a repó tulajdonosaként futtatja az ágenst — rootful Dockeren átvált annak az uid-jére, rootless Dockeren a host felhasználó eleve uid 0 a konténerben.

Helyi Modell Futtatókörnyezet

  • ollama szolgáltatás: az ollama/ollama első induláskor letölti a modellt egy volume-ba, és csak utána egészséges; az ágens a http://ollama:11434 címen éri el (nincs host port).
  • Hoston futtatva (make p1 ... make bonus) a make setup által indított, :11436 porton futó Ollamát használja.
  • Modell: qwen2.5-coder:1.5b (1,54 milliárd paraméter, a 3 milliárdos korlát alatt).
  • Embedding: all-MiniLM-L6-v2, a /tmp/iow/hf-cache-ben, offline töltve.
Defense Tipp: Az értékelők ellenőrzik, hogy nincs-e felhőhívás. Az ágens minden végpontja helyi: Ollama, a célalkalmazás és a Gitea — lásd az OLLAMA_HOST-ot a docker-compose.yml-ban.

Part 1: Observer (A Szenzoros Hálózat)

Docker Figyelő

A célkonténer állapota és eseményei a Docker démontól:

  • Nem-nulla exit az eseményfolyamból (a restart policy elrejti a lekérdezés elől)
  • Restart loop (növekvő számláló, vagy beragadt újraindulás)
  • Dead / OOM-killed állapot
  • Túléli a démon kiesését és újracsatlakozik

Valós Idejű Log Streamer

Követi a konténer kimenetét:

  • 500 soros szálbiztos körpuffer
  • Konfigurálható regex hibaminták (target.error_patterns)
  • Egy traceback = egy incidens; a visszajátszott múlt nem vált ki újra eseményt
  • SSE eseménycsatorna a webes felületre

HTTP Szondák és Osztályozás

3 másodpercenként lekérdezi a target.probe_urls címeit (/, /healthz, /api/missing-route):

  • 2xx: Egészséges működés
  • 4xx: Soft szuggesztió (EMBERI feladat, nem javítja automatikusan)
  • 5xx / elutasított kapcsolat / timeout: Hard crash jelzés
Csúszóablakos Deduplikáció: egy incidens = egy esemény számlálóval (90 mp-es ablak, hosszabb a Docker 60 mp-es maximális restart-várakozásánál; szuggesztióknál 300 mp). Az incidens véget ér, amint a cél újra kiszolgál, vagy egy javítás verifikált.

Part 2: Analyst (Szemantikus Keresés és Diagnózis)

AST Logikai Daraboló (chunker.py)

  • A subject kifejezetten tiltja a fix méretű darabolást (pl. 500 karakter).
  • Python ast: függvényenként, osztályonként és metódusonként egy chunk, plusz a modulszintű blokkok és a __main__ blokk — minden sor benne van egy chunkban.
  • Chunkonkénti SHA-256: a változatlan chunk soha nem embeddelődik újra.
  • ChromaDB PersistentClient a /tmp/iow/chroma_db-ben; watch mode 3 mp-enként újraindexeli a változott fájlokat, és törli, ami eltűnt.

Traceback Által Vezérelt RAG

  • A traceback függvényeit és fájl:sor kereteit magában az indexben keresi meg.
  • Ezeket egy koszinusz top-k kereséssel egyesíti (helyi all-MiniLM-L6-v2).
  • Csak ezek a chunkok kerülnek a promptba — a modell választ, nem talál ki.

Strukturált JSON Diagnózis és Anti-Hallucináció

Szigorú JSON kimenetet kényszerít ki: {"summary": "...", "files": ["eleresi/ut"]}. A gyanúsított fájlokat összeveti a valós indexelt fájlokkal — az ágens nem találgat és nem nyúl képzeletbeli elérési utakhoz.

Part 3: Wisdom Loop (Cselekvés és Rollback)

Diff-mentes JSON Patcher

A patch {summary, files: [{path, op, content}]} a teljes módosított fájllal, az op create / modify / delete; diffet nem fogad el. Nagyobb fájlban a modell csak azt a chunkot írja újra, ahová a hiba mutat, és a patcher építi meg a teljes fájlos patchet (analyst.patch_strategy: full_file esetén a modell írja meg egészben).

Sanity Bounds (Lemezre írás előtt)

  • Legfeljebb 3 fájlt módosíthat
  • Nem lehet triviális placeholder
  • Max. 60%-os méretcsökkenés
  • Nem szivároghatnak RAG markerek
  • Csak demo_app/, soha az iow.config.yml
  • Parse-olnia kell, változtatnia kell, és nem tűnhet el definíció

GitManager és Ágkezelés

Pre-loop revízióként rögzíti a demo_app/ pontos futó állapotát (snapshot commit, ha eltér a HEAD-től), atomian ír (*.iow.tmp + fsync + os.replace), és git plumbinggal commitol az iow/auto-heal ágra — a HEAD, az index és a kicheckoutolt ág nem mozdul.

A 3-Kísérletes Garancia: 3 sikertelen kísérlet után az iow/auto-heal visszaáll a pre-loop revízióra, a demo_app/ egy eldobható indexen át helyreáll belőle, az újrahash-elt fa identical, és a cél ezen indul újra. Egy ágensleállítás miatt félbemaradt ciklus a következő induláskor visszaáll.

Dinamikus Biztonsági Korlátok (iow.config.yml)

Hard-code-olt időzítések tiltottak. Minden beállítás közvetlenül lemezről frissül:

Az 5 Megkerülhetetlen Szabály

  • Single-Flight: Egyszerre pontosan 1 javítási ciklus futhat. Kizárja a versenyhelyzeteket.
  • Cooldown: 300 mp türelmi idő ugyanarra a hiba-szignatúrára.
  • Rate Limit: Legfeljebb 5 javítás egy csúszó órán belül.
  • Hard Cap: Legfeljebb 20 javítás a folyamat élettartama alatt.
  • Kill-Switch: A kill_switch: true azonnal tilt minden új kísérletet.

Dinamikus mtime Újratöltő

A SafetyManager figyeli a fájl módosítási idejét (os.path.getmtime). A konfiguráció átírása azonnal érvényesül az ágens vagy a konténer újraindítása nélkül!

# demo_app/iow.config.yml
grace_period: 20
cooldown: 300
rate_limit_per_hour: 5
hard_cap: 20
boot_timeout: 45
kill_switch: false

Chapter VI: Bónusz Képességek (bonus/)

Tiny Symptom Classifier

Minden verifikált javítást megtanul, azzal a kóddal együtt, amelyre alkalmazták. Ugyanaz a hiba ugyanazon a kódon a tárolt patchből gyógyul, LLM hívás nélkül: az újraindítás és a grace period alatt (az alapértelmezett 20 mp-cel 24 mp), 45-80 mp helyett. A sikertelen tárolt patch bizalmat veszít.

Second Opinion Konszenzus

Két prompt (konzervatív stack frame vs hívói szerződés) egyezzen meg a gyanús fájlban — minden kísérletnél, az újrapróbálkozásoknál is. Eltérés esetén soha nem javít önállóan. Alapból kikapcsolva, a Bónusz fülön kapcsolható.

Human-in-the-Loop PR-ek

HITL módban semmi nem kerül be emberi jóváhagyás előtt: review PR (iow/review/<ciklus>) a helyi Giteán, a diffjével. A jóváhagyott kód a javítási korlátok alatt települ, és csak akkor marad, ha a cél fennmarad.

A Gitea a make up-pal (hoston: make pr-bonus) a :3000 porton fut. GitOps: make argocd-bonus (campus-biztos iow-k3s, Argo UI :8080 vagy IOW_ARGOCD_PORT, demo NodePort :30051); hibát a klaszterbe a make break-import gitops-publish ültet. Ott maga a javító commit telepít: a kódja hash-ét a pod sablonba írja, az Argo CD szinkronizálja és új podot indít.

Védési Demonstráció Menete

1. Lépés: Indítás és Alapállapot

# Ágens + LLM futtatókörnyezet + cél + Gitea
make up

# Nyisd meg a Dashboardot:
http://localhost:8000

# Gyorsítás a védéshez (élőben, újraindítás nélkül):
# grace_period: 5 a demo_app/iow.config.yml-ben

Mutasd meg az értékelőknek: a cél fut és egészséges (zöld jelvény), élő logstream folyik, még nincs crash esemény.

2. Lépés: Indulási hiba ültetése

# hiányzó import (vagy: make break-env / break-syntax)
make break-import

Kövesd végig a képernyőn a 4 ütemet:

  1. Az Observer egy crash eseményt kelt (exit kód, restart loop, traceback).
  2. Státusz sárgára vált ("HEALING IN PROGRESS").
  3. Az Analyst a demo_app/app.py-t nevezi meg.
  4. A patch átmegy a sanity kapun, és commit lesz az iow/auto-heal ágon.
  5. A cél újraindul, és ki kell bírnia a grace periodot.
  6. A kísérlet "VERIFIED HEALED" lesz, diffel együtt, a Wisdom Loop fülön.

A make break / break-hard szándékosan összeomló végpontokat hív: a modell vagy átírja a végpontot, amíg az újraküldött kérés 2xx-et nem ad, vagy nem változtat rajta — ekkor a hurok visszaáll, identical eredménnyel.
