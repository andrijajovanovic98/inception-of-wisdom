Part 1: Observer — The Nervous System

The Observer's responsibility is to continuously monitor target container lifecycle events, follow stdout/stderr logs in real time, probe HTTP endpoints, classify failure signals, and deduplicate incidents into a clean event stream.

Subject Requirement: "Observe: inspect Docker events, follow the log stream in near real time, probe HTTP endpoints, and deduplicate events into a single incident."

Docker Socket Inspection (docker_monitor.py)

Socket Communication

Mounting /var/run/docker.sock into the agent enables direct communication with the host Docker engine via the Python docker SDK.

  • Non-zero exit detection: status == "exited" and exit_code != 0
  • Crash loop detection: status == "restarting" with restart count
  • Dead state: c_state.get("Dead") or c_state.get("OOMKilled")

Container Lifecycle Actions

The DockerMonitor provides resilient restart primitives:

def restart_container(self, timeout=10):
    container = client.containers.get(self.container_name)
    container.restart(timeout=timeout)
    return True
Evaluator Question: "What happens if Docker daemon restarts?"
Answer: DockerMonitor catches API exceptions and lazily reconnects without crashing the agent.

Real-Time Log Streamer (log_streamer.py)

Stream Loop & Ring Buffer

  • Follows container.logs(stream=True, follow=True) in a dedicated background worker thread.
  • Maintains a 500-line thread-safe ring buffer (collections.deque(maxlen=500)).
  • Yields real-time events to the dashboard via Server-Sent Events (SSE).

Regex Error Matching

Scans each line against compiled regex patterns:

DEFAULT_ERROR_PATTERNS = [
    r"Traceback \(most recent call last\):",
    r"CRITICAL:",
    r"Error:",
    r"Exception:"
]

When matched, immediately signals the central EventManager.

HTTP Probes & Signal Classification (http_probe.py)

Hard Crash vs Soft Suggestion

The subject strictly requires separating hard crashes from suggestions:

  • Hard Signal (Crash):
    • HTTP 5xx Server Error
    • Connection refused / dropped socket
    • Timeout (target unresponsive)
    • 👉 Triggers the Wisdom Loop automatically!
  • Soft Signal (Suggestion):
    • HTTP 4xx (e.g. 404 Not Found, missing route)
    • 👉 Surfaced on dashboard for humans. NEVER patched automatically!

Continuous Poller

Runs every probe_interval_seconds (read dynamically from iow.config.yml):

# demo_app/iow.config.yml
target:
  service_url: "http://demo_app:5000"
  probe_interval_seconds: 3
  probe_urls: ["/", "/healthz"]

Reports response time in milliseconds for the dashboard latency monitor.

Event Deduplication (event_manager.py)

The Flooding Problem

When a container fails to start, Docker restart loops or polling probes can emit 50 errors per minute. Without deduplication, the LLM would be flooded with duplicate tickets.

Sliding-Window Solution

  • Computes SHA-256 fingerprint: SHA256(source + type + raw_key).
  • Maintains sliding-window timestamp cache:
    • Crash window: 10 seconds
    • Suggestion window: 60 seconds
  • Duplicate events within the window increment a counter (x3) instead of generating new notifications.
Result: 1 real root cause = 1 clean ObserverEvent.

Observer REST API & SSE Channel (observer_api.py)

FastAPI Endpoints

  • GET /api/observer/status: Container health, Docker state, HTTP latency.
  • GET /api/observer/logs: Snapshot of the recent ring buffer logs.
  • GET /api/observer/events: List of deduplicated incident events.
  • GET /api/observer/stream: Server-Sent Events (SSE) real-time event pipeline streaming directly into the browser terminal.
Defense Tip: Show the evaluators how the web terminal autoscrolls as the target container starts and outputs logs via SSE!

Part 1 Peer-Evaluation Checklist

Key Questions Evaluators Will Ask:

  • Q: How does the Observer know the container is down?
    A: Dual detection: Docker socket status (exited, restarting, dead) AND HTTP probe failures (5xx, connection refused).
  • Q: Why are 4xx errors not automatically patched?
    A: Subject specification: 4xx indicates a missing feature or client error (soft suggestion), not a service crash. Only hard failures trigger automated code repair.
  • Q: How is log flooding prevented?
    A: Sliding-window deduplication in event_manager.py groups recurring signatures over a 10s window.
