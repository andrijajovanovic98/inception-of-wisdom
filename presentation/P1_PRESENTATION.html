Part 1: Observer — The Nervous System

The Observer's responsibility is to continuously monitor target container lifecycle events, follow stdout/stderr logs in real time, probe HTTP endpoints, classify failure signals, and deduplicate incidents into a clean event stream.

Subject (V.1): "The container side reports the target's current state (running, restarting, exited), streams its standard output and standard error in near real time, and raises a crash event whenever the container exits with a non-zero status, enters a restart loop, or emits a line that matches a configurable list of error patterns."

Docker Socket Inspection (docker_monitor.py)

Socket Communication

The daemon's socket ($DOCKER_SOCK, mounted as /var/run/docker.sock) gives the agent the host Docker engine through the Python docker SDK.

  • Non-zero exit: the event stream's die with its exitCode — with restart: unless-stopped the exited state lasts milliseconds, so polling alone never sees it. The kill of our own restart explains exactly one exit.
  • Restart loop: the restart counter climbing within 60 s, or the container stuck in restarting.
  • Dead state: State.Dead, State.OOMKilled and the oom event.
  • Stopped on purpose: after docker stop / kill the container stays exited and its restart policy leaves it down; docker pause leaves it paused. The Observer reports the outage, but no heal starts — there is no code to fix.

Container Lifecycle Actions

The DockerMonitor provides resilient restart primitives:

def restart_target(self, timeout=10):
    container = client.containers.get(self.container_name)
    if container.status == "running":
        self.mark_deliberate()  # our own stop is no crash
    container.restart(timeout=timeout)
    return True
Evaluator Question: "What happens if Docker daemon restarts?"
Answer: the agent keeps answering; the target reads daemon_unavailable (not a crash), one warning per outage is logged, and the event stream resumes at the last event it handled — no crash lost, none replayed.

Real-Time Log Streamer (log_streamer.py)

Stream Loop & Ring Buffer

  • Follows container.logs(stream=True, follow=True, timestamps=True) in a background worker that re-attaches after every restart.
  • Lines logged before the agent started, or before a deliberate restart, are history: judged by the log's own timestamps, they never raise a crash.
  • 500-line thread-safe ring buffer; tracebacks keep their indentation.
  • Every line goes to the dashboard over Server-Sent Events (SSE).

Regex Error Matching

Scans each line against the configurable patterns (live from iow.config.yml):

target:
  error_patterns:
    - "Traceback \\(most recent call last\\):"
    - "CRITICAL:"
    - "\\w*(?:Error|Exception):"
    - "ModuleNotFoundError"
    - "ImportError"
    - "SyntaxError"

Matching lines within incident_debounce_seconds are one incident: a whole traceback reaches the EventManager as a single error.

HTTP Probes & Signal Classification (http_probe.py)

Hard Crash vs Soft Suggestion

The subject strictly requires separating hard crashes from suggestions:

  • Hard Signal (Crash):
    • HTTP 5xx Server Error
    • Connection refused / dropped socket
    • Timeout (target unresponsive)
    • → Triggers the Wisdom Loop automatically!
  • Soft Signal (Suggestion):
    • HTTP 4xx (e.g. 404 Not Found, missing route)
    • → Surfaced on dashboard for humans. NEVER patched automatically!

Continuous Poller

Runs every probe_interval_seconds (read dynamically from iow.config.yml):

# demo_app/iow.config.yml
target:
  service_url: "http://demo_app:5000"
  probe_interval_seconds: 3
  probe_urls: ["/", "/healthz", "/api/missing-route"]

The last one answers 404 on purpose: a suggestion. A dead target (refused, timed out) is one target-unreachable event, not one per URL.

Inside Compose the agent uses http://demo_app:5000; host-run commands use TARGET_URL=http://127.0.0.1:5001.

Reports response time in milliseconds for the dashboard latency monitor.

Event Deduplication (event_manager.py)

The Flooding Problem

When a container fails to start, Docker restart loops or polling probes can emit 50 errors per minute. Without deduplication, the LLM would be flooded with duplicate tickets.

Sliding-Window Solution

  • Computes SHA-256 fingerprint: SHA256(source + type + raw_key).
  • Maintains sliding-window timestamp cache:
    • Crash window: 90 seconds (sliding, crash_dedup_window_seconds) — longer than Docker's 60 s maximum restart backoff, so a long crash loop stays one event (at least 330 s in GitOps mode: Kubernetes backs off up to 300 s)
    • Suggestion window: 300 seconds (suggestion_dedup_window_seconds)
  • Duplicate events within the window increment a counter (x3) instead of generating new notifications.
  • An incident ends once the target serves again, or when a heal is verified: the same crash planted again is a new event.
Result: 1 real root cause = 1 clean ObserverEvent.

Observer REST API & SSE Channel (observer_api.py)

FastAPI Endpoints

  • GET /api/observer/status: Container health, Docker state, HTTP latency.
  • GET /api/observer/logs: Snapshot of the recent ring buffer logs.
  • GET /api/observer/events: List of deduplicated incident events.
  • GET /api/observer/stream (also GET /events): Server-Sent Events (SSE) — log lines, crash events and heartbeats, straight into the browser terminal.
Defense Tip: Show the evaluators how the web terminal autoscrolls as the target container starts and outputs logs via SSE!

Part 1 Peer-Evaluation Checklist

Key Questions Evaluators Will Ask:

  • Q: How does the Observer know the container is down?
    A: Dual detection: Docker socket status (exited, restarting, dead) AND HTTP probe failures (5xx, connection refused).
  • Q: Why are 4xx errors not automatically patched?
    A: Subject specification: 4xx indicates a missing feature or client error (soft suggestion), not a service crash. Only hard failures trigger automated code repair.
  • Q: How is log flooding prevented?
    A: Sliding-window deduplication in event_manager.py groups recurring signatures over a sliding window (90 s for crashes, 300 s for suggestions, both in iow.config.yml).
