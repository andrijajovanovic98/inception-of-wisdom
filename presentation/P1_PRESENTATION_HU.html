Part 1: Observer — A Szenzoros Idegrendszer

Az Observer feladata a célkonténer életciklusának folyamatos monitorozása, a stdout/stderr logok valós idejű követése, HTTP szondák futtatása, a hibajelzések osztályozása és a hibaesemények deduplikációja.

Subject (V.1, fordítás): "A konténer oldal jelenti a cél aktuális állapotát (running, restarting, exited), szinte valós időben streameli a standard kimenetét és hibakimenetét, és crash eseményt kelt, valahányszor a konténer nem-nulla státusszal kilép, restart loopba kerül, vagy olyan sort ír, amely illeszkedik a hibaminták konfigurálható listájára."

Docker Socket Vizsgálat (docker_monitor.py)

Socket Kommunikáció

A démon socketje ($DOCKER_SOCK, a konténerben /var/run/docker.sock) a Python docker SDK-n át adja az ágensnek a host Docker motorját.

  • Nem-nulla exit: az eseményfolyam die eseménye az exitCode-dal — restart: unless-stopped mellett az exited állapot ezredmásodpercekig tart, lekérdezéssel nem látszik. A saját újraindításunk kill-je pontosan egy kilépést magyaráz.
  • Restart loop: 60 mp-en belül növekvő újraindítás-számláló, vagy restarting-ben beragadt konténer.
  • Halott konténer: State.Dead, State.OOMKilled és az oom esemény.
  • Szándékos leállítás: docker stop / kill után a konténer exited marad, a restart policy nem indítja újra; docker pause után paused. Az Observer jelzi a kiesést, de javítás nem indul — nincs mit javítani a kódban.

Konténer Újraindítás

A DockerMonitor ellenálló újraindító primitívet nyújt:

def restart_target(self, timeout=10):
    container = client.containers.get(self.container_name)
    if container.status == "running":
        self.mark_deliberate()  # a saját leállításunk nem crash
    container.restart(timeout=timeout)
    return True
Értékelői Kérdés: "Mi történik, ha a Docker démon újraindul?"
Válasz: az ágens tovább válaszol; a cél állapota daemon_unavailable (nem crash), kiesésenként egy figyelmeztetés kerül a logba, és az eseményfolyam az utoljára kezelt eseménytől folytatódik — nem vész el és nem ismétlődik crash.

Valós Idejű Log Streamer (log_streamer.py)

Stream Ciklus és Körpuffer

  • Követi a container.logs(stream=True, follow=True, timestamps=True) folyamot egy háttérszálban, amely minden újraindulás után újracsatlakozik.
  • Az ágens indulása vagy egy szándékos újraindítás előtt logolt sorok múltnak számítanak: a log saját időbélyegei alapján soha nem váltanak ki crash-t.
  • 500 soros szálbiztos körpuffer; a tracebackek megtartják a behúzásukat.
  • Server-Sent Events (SSE) csatornán minden sor azonnal a dashboardra kerül.

Regex Hibaminta Illesztés

Minden sort összevet a konfigurálható mintákkal (élőben az iow.config.yml-ből):

target:
  error_patterns:
    - "Traceback \\(most recent call last\\):"
    - "CRITICAL:"
    - "\\w*(?:Error|Exception):"
    - "ModuleNotFoundError"
    - "ImportError"
    - "SyntaxError"

Az incident_debounce_seconds-on belül illeszkedő sorok egy incidenst alkotnak: egy teljes traceback egyetlen hibaként jut az EventManager-hez.

HTTP Szondák és Jelzésosztályozás (http_probe.py)

Hard Crash vs Soft Szuggesztió

A subject szigorúan megköveteli a hibák és szuggesztiók szétválasztását:

  • Hard Signal (Crash):
    • HTTP 5xx Server Error
    • Connection refused / megszakadt kapcsolat
    • Timeout (nem válaszoló célalkalmazás)
    • → Automatikusan elindítja a Wisdom Loop öngyógyítást!
  • Soft Signal (Szuggesztió):
    • HTTP 4xx (pl. 404 Not Found, hiányzó route)
    • → Csak megjelenik a dashboardon az ember számára. SOHA nem javítja automatikusan!

Folyamatos Poller

Időzítése az iow.config.yml fájlból olvasandó:

# demo_app/iow.config.yml
target:
  service_url: "http://demo_app:5000"
  probe_interval_seconds: 3
  probe_urls: ["/", "/healthz", "/api/missing-route"]

Az utolsó szándékosan 404-et ad: szuggesztió. Egy halott cél (elutasított kapcsolat, timeout) egyetlen target-unreachable esemény, nem URL-enként egy.

Compose-on belül az ágens a http://demo_app:5000 címet használja; hoston futtatva a cím TARGET_URL=http://127.0.0.1:5001.

Késleltetést mér milliszekundumban a felület számára.

Esemény Deduplikáció (event_manager.py)

Az Eseményáradat Problémája

Ha a konténer beragad egy újraindulási hurokba, percenként több tucat hiba keletkezik. Deduplikáció nélkül az LLM túlterhelődne az azonos hibaüzenetekkel.

Csúszóablakos Megoldás

  • SHA-256 ujjlenyomat: SHA256(forras + tipus + kulcs).
  • Csúszóablakos időbélyeg cache:
    • Crash ablak: 90 másodperc (csúszó, crash_dedup_window_seconds) — hosszabb a Docker 60 mp-es maximális restart-várakozásánál, így egy hosszú crash loop egy esemény marad (GitOps módban legalább 330 mp: a Kubernetes akár 300 mp-et vár két újraindítás között)
    • Szuggesztió ablak: 300 másodperc (suggestion_dedup_window_seconds)
  • Az ablakon belül érkező duplikátumok egy számlálót léptetnek (x3) új esemény dobása helyett.
  • Az incidens véget ér, amint a cél újra kiszolgál, vagy egy javítás verifikált: ugyanaz a hiba újra elültetve új esemény.
Eredmény: 1 valós hibaforrás = 1 tiszta ObserverEvent.

Observer REST API és SSE Csatorna (observer_api.py)

FastAPI Végpontok

  • GET /api/observer/status: Konténer állapot, Docker státusz, HTTP késleltetés.
  • GET /api/observer/logs: A körpuffer legutóbbi sorainak pillanatképe.
  • GET /api/observer/events: A deduplikált incidensek listája.
  • GET /api/observer/stream (vagy GET /events): Server-Sent Events (SSE) — logsorok, crash események és heartbeat a webes terminálhoz.
Defense Tipp: Mutasd meg a vizsgáztatóknak, hogyan gördülnek valós időben a logok a fekete terminálablakban az SSE-n keresztül!

Part 1 Védési Kérdések és Válaszok

Gyakori Értékelői Kérdések:

  • K: Honnan tudja az Observer, hogy a konténer összeomlott?
    V: Kétirányú detektálás: a Docker socket állapota (exited, restarting, dead) ÉS a HTTP szondák (5xx, connection refused).
  • K: Miért nem javítja automatikusan a 4xx hibákat?
    V: Subject előírás: a 4xx funkcionális hiányosságot vagy klienshibát jelent, nem pedig rendszerszintű összeomlást. Csak a hard hibák aktiválják az öngyógyítást.
  • K: Hogyan akadályozod meg az eseményáradatot?
    V: Az event_manager.py csúszóablakos deduplikációja SHA-256 ujjlenyomat alapján a csúszó ablakon belül (crash: 90 mp, szuggesztió: 300 mp, mindkettő az iow.config.yml-ben) egyetlen incidenssé vonja össze az ismétlődő hibákat.
