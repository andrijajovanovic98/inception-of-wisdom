Part 3: Wisdom Loop — Autonomous Remediation

The Wisdom Loop turns diagnostic insights into verified source code repairs. It coordinates diff-free JSON patching, multi-stage sanity checks, atomic Git branch management, Docker container lifecycle restarts, active verification polling, and automatic multi-attempt rollback.

Subject (V.3): "Given a diagnosis, the loop generates a patch, applies it, commits, restarts the target, and decides whether the symptom is gone." — "After three failed attempts, the Wisdom Loop rewinds the auto-heal branch to the pre-loop revision (the agent's commits become unreachable), restarts the target on the original code, and surfaces a clean failure to the dashboard."

Diff-Free JSON Patching (p3/patcher.py)

Why Unified Diffs Fail with Small LLMs

Standard diffs (@@ -12,4 +12,6 @@) require exact character counts and line offset mathematics. Models under 3B parameters consistently hallucinate diff headers, producing malformed patches that patch(1) rejects.

Structured JSON File Replacement

{
  "summary": "Restore the Flask import the startup code needs",
  "files": [
    {
      "path": "demo_app/app.py",
      "op": "modify",
      "content": "... the complete post-change file ..."
    }
  ]
}
  • content is the complete post-change file; op is create, modify or delete. A diff is refused.
  • No canned fixes: in a larger file the model rewrites only the chunk the traceback points at (plain code), and the patcher splices it into the complete file of the JSON patch. analyst.patch_strategy: full_file has the model write the whole JSON patch itself (a 1.5B model cuts the file short — measured 0 of 9).
  • An answer handed back unchanged, or one that only moves the failure (a new raise / exit(), the server started under a condition), is asked for again inside the attempt — before it costs a redeploy.

Sanity Bounds & Guardrails (p3/sanity.py)

Pre-Disk Safety Screening

Before any patch touches the filesystem or Git tree it must pass the subject's four rules, and four more:

  • File Count Bound: max 3 files per patch.
  • Trivial Placeholder: a non-empty file may not become a stub (pass, ..., a docstring); no new # TODO or rest of code unchanged.
  • Shrinkage Guard: max 60% smaller than the original, whatever the op says (a create over an existing file counts, deleting a non-empty file is a 100% shrink) and whatever its size.
  • Retrieval Markers: prompt scaffolding (--- File: ... ---, --- Code Snippet #n ---, region fences) may not leak into the code.
  • Scope: only paths inside demo_app/, never the operator's iow.config.yml.
  • Parses and changes something: ast.parse must succeed, and a patch identical to the file is refused.
  • No lost definitions: a rewrite may not drop an import or constant the file still uses.
  • No value read before it is set: port set only inside an if, or a try whose except falls through, is refused (a NameError after the redeploy).

Git Isolation & Atomic Commits (p3/git_manager.py)

Dedicated Healing Branch

  • All self-healing work occurs on isolated branch: iow/auto-heal.
  • Records the exact state demo_app/ runs as the pre-loop revision: HEAD when the tree matches it, else a snapshot commit (an uncommitted planted bug included), kept in refs/iow/pre-loop until the cycle ends.
  • Atomic file writing: *.iow.tmp + fsync + os.replace, file mode kept.
  • Commits with git plumbing, the subject line generated from the diagnosis: HEAD, the index and the checked-out branch never move.

Byte-for-Byte Rollback

Proven, not assumed: after 3 failed attempts iow/auto-heal is rewound to the pre-loop revision and demo_app/ is restored from it through a throwaway index (read-tree + checkout-index). The tree is re-hashed and compared: the dashboard shows identical. The operator's iow.config.yml is kept, and an edit made during the cycle is saved under refs/iow/overwritten/<time> first.

Container Restart & Verification (p3/verifier.py)

Docker Engine Restart

  • Interacts with host Docker daemon via /var/run/docker.sock.
  • Restarts the target via Docker Engine API by default.
  • With IOW_REDEPLOY_MODE=gitops, pushes the commit instead and waits for the pod Argo CD rolls from it (the commit stamps its code's hash into the pod template).
  • Captures new container state and exit status.

Active Grace Period (20s)

  • Waits until the target answers once (boot_timeout), then starts the grace period.
  • Replays the request that crashed the target, read from its own log (Flask's Exception on /api/crash [POST], the 5xx access line): a soft crash on a route no probe calls cannot pass as healed.
  • Any crash event, a non-zero exit of the new process, or failing probes during the grace period fail the attempt.

Feedback Loop & Retry Orchestration (p3/loop.py)

Adaptive Multi-Turn Healing

A single attempt may not fully resolve deep architectural bugs. The Wisdom Loop adapts across 3 turns:

Attempt 1: Initial Diagnosis -> Patch -> Restart -> Verification Fails!
                 │
                 ▼ (Feedback: Container exited with status 1, Traceback included)
Attempt 2: Augmented Prompt with Failure Context -> Refined Patch -> Pass!
                 │
                 └─ If Attempt 3 fails: rollback to the pre-loop revision (verified identical)
  • The new error log — read from the daemon since the restart — goes back to the Analyst.
  • The next patch prompt hears what failed (and whether its own change caused it), samples more freely (temperature 0.1 / 0.4 / 0.7) and, for environment problems, is told the target's port and environment as read from its container.

Safety Controls & Dynamic Limits (p3/safety.py)

iow.config.yml Constraints

  • Single-Flight Lock: Only one healing loop can run concurrently.
  • Cooldown: Enforces 300s quiet time for the same incident signature.
  • Rate Limit Per Hour: Caps repairs at 5 per rolling 60-minute window.
  • Hard Cap: Allows at most 20 repairs per process lifetime.

Emergency Kill-Switch

Subject Requirement: Setting kill_switch: true in iow.config.yml immediately disables the loop without restarting the agent!

Part 3 Peer-Evaluation Checklist

Key Questions Evaluators Will Ask:

  • Q: Why did you not use git apply with unified diff?
    A: LLMs < 3B hallucinate line offsets in diff headers. Full-file replacement eliminates syntax patch corruption while staying within sanity limits.
  • Q: What prevents the AI from deleting the whole codebase to 'fix' a bug?
    A: The sanity gate, before any disk write: max 3 files, no trivial placeholder, a 60% shrinkage guard, no lost definitions, no value read before it is set, and the code must still parse.
  • Q: How do you prove rollback works during the defense?
    A: Stop the model (make stop for the host Ollama, docker stop iow_ollama in Docker), plant a crash and watch 3 failed attempts, then the rollback: demo_app/ hashes back to the pre-loop tree (identical) and unrelated work is untouched.
